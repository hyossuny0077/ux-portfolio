CASE 01 · 시니어 케어 테크 스타트업 · 2026.05–10

지켜보되 간섭하지 않는 돌봄

혼자 사는 어르신의 안부를 AI 기기가 먼저 묻고, 사람이 해야 할 일만 운영자에게 올려주는 돌봄 UX를 설계했습니다. 서로 다른 네 사람의 불안을 하나의 원칙으로 묶어 화면과 기능명세로 옮긴 과정입니다.

역할프로덕트 디자이너(UI/UX) — 팀 10명(기획1·디자인1(본인)·개발4·사업부2·운영/CS2) 중 유일한 디자이너
도구Figma, Claude, Notion, HTML 명세서, Bitbucket
기여 범위위험 대응 기준처럼 사업부·기획팀이 협의해 정한 정책은 팀이 정한 것. 그 결정을 명세·화면에 반영하고 AI엔 초안·반복·누락 확인을 맡긴 것은 직접 한 것
12종 같은 틀로 작성한 기능명세

01Background

서로 다른 네 사람의 불안, 하나의 원칙

이 서비스에는 사용하는 사람이 네 명 있고, 이들은 서로 다른 것을 걱정합니다. 지켜보고 싶지만 간섭은 싫고, 출동은 줄이고 싶지만 안전은 지켜야 합니다.

사용자페르소나핵심 문제
어르신 이정숙 (76세) 혼자 지내는 시간이 길어 복약과 일정을 놓치고 위급 상황이 불안하지만, 자녀에게 부담을 주기는 싫다
보호자 김서현 (48세) 자주 연락할 수 없어 부모의 안전과 변화를 알기 어렵지만, 간섭처럼 느껴지는 것은 피하고 싶다
현장 운영자 김철수 (42세) 오작동과 실제 응급을 가려내느라 시간을 쓰고, 현장 조치 뒤에도 행정 처리를 해야 한다
기관 관리자 김지현 (55세) 무엇이 먼저인지 한눈에 알기 어렵고, 대면 출동은 줄이면서 안전은 지켜야 한다

이 충돌을 풀 기준으로 네 가지 방향을 세웠습니다: 의료적 접근보다 생활 중심으로, 감시보다 세심하게 살피는 방식으로, 보호보다 독립성을 존중하는 방식으로, 기술은 드러나지 않고 도움이 느껴지도록.

02Before / After

태블릿에서 AI 돌봄 로봇으로 — 역할의 재정의

기존 태블릿 중심 인터페이스는 사용자가 직접 기능을 탐색하고 화면을 터치해야 했습니다. 디지털 기기 사용이 익숙하지 않은 어르신에게는 기능을 찾고 실행하는 과정 자체가 진입장벽이었습니다. 제품의 역할을 "화면을 터치해 실행하는 기기"에서 "말을 걸면 의도를 파악해 실행하는 대화 상대"로 다시 정의하면, 그 부담을 줄일 수 있다는 가설을 세웠습니다.

Before · 터치로 실행

[스크린샷: 기존 태블릿 메뉴 탐색 화면]

사용자가 화면에서 기능을 찾고, 메뉴를 선택하고, 실행한다.

After · 대화로 실행

정해진 명령어 없이 말로 쓴다. 원하는 행동을 자연스럽게 말하면 기기가 의도를 파악해 기능을 실행한다.

자유대화로 할 수 있는 것

정해진 메뉴를 거치지 않고 말로 바로 처리합니다 — 복약 확인, 음악·라디오 재생, 기기 설정, 안부 확인, 말벗·날씨, 위급 시 119 연결까지. 화면에는 따라 말할 수 있는 예시 문구를 함께 보여줘서, 무엇을 말해야 할지 몰라도 막히지 않게 했습니다.

03Familiar Interaction

어르신에게 익숙한 방식을 그대로

디지털 기기 이전에 익숙했던 방식(TV·라디오 채널을 손으로 돌리거나 버튼으로 넘기는 아날로그 조작)을 그대로 인터페이스에 들여오는 대신, 그 방식이 주던 느낌(바로 되고, 실수해도 괜찮은)을 음성으로 옮기려 했습니다.

Case · 채널 선택 — 목록 탐색 대신 말로 바로

Problem
라디오 채널이 목록으로 나열되는 화면은, 평생 아날로그 다이얼이나 버튼으로 채널을 넘겨 온 어르신에게 낯선 탐색 방식이다
Why
어르신에게 새 탐색 방식을 학습시키기보다, 이미 익숙한 "말하면 바로 틀어지는" 감각에 가깝게 만드는 편이 진입장벽을 낮춘다
Hypothesis
채널 이름을 직접 말하게 하면 목록을 눈으로 훑고 고르는 과정 자체를 없앨 수 있을 것이다
Design
"OO 라디오 틀어줘"처럼 채널명을 바로 말하면 재생, 채널을 말하지 않으면 마지막으로 듣던 채널을 이어서 재생. 다음 채널로 넘기는 음성 명령도 함께 지원
Open question
음성 인터페이스를 쓰지 않거나, 말이 어눌한 사람은 어떻게 하는가? 음성이 모든 사용자의 문제를 해결하지 않는다고 보고, 화면에서 직접 채널을 골라 누르는 터치 방식도 그대로 남겨 두어 음성과 터치를 함께 지원하게 했다
Next step
지금은 설계 단계의 해결 방향이며, 실제 사용자 관찰을 통한 검증은 다음 과제로 남겨 두었다

Case · 반복 안내 — 한 번 설명으로 충분한가

Problem
기능을 한 번 안내한다고 해서 어르신이 그 기능을 기억하고 이후에 스스로 쓸 수 있는 것은 아니다
Why
한 번의 설명은 그 순간 이해돼도 금방 잊히기 쉽고, 어르신에게는 반복 노출이 학습에 더 유효하다고 보았다
Hypothesis
앱을 열 때마다 짧은 안내를 음성으로 반복해서 들려주면, 긴 설명 한 번보다 주요 기능을 자연스럽게 익히게 될 것이다
Design
앱 진입 시 뜨는 스플래시 화면에서 최소 노출 시간 동안 짧은 기능 안내를 음성으로 함께 전달하도록 설계
Validation
주요 기능 인지율, 최초 실행 성공률, 기능 재사용률, 도움 요청 빈도를 추적 지표로 설계했으나, 실제 사용 데이터로 가설을 검증하는 단계까지는 진행하지 못했다 — 검증 예정
04UX Case Studies

설계 판단을 보여주는 세 가지 사례

Case 01 · UI 테스트 — 대조를 절차로 바꾸다

Problem
기기와 관리자 웹이 실시간으로 연동되는 구조라, 문구나 정책이 바뀔 때마다 기능명세서에 일일이 반영해야 했고 눈으로만 대조하면 놓치기 쉬웠다
Why
한 번 맞추는 것보다, 바뀔 때마다 다시 맞추는 과정을 싸게 만드는 것이 더 중요하다
Hypothesis
AI로 화면 단위 대조를 하면 사람이 눈으로 하는 것보다 빠르고, 반복 가능한 절차로 만들 수 있을 것이다
Design
설치 과정 10개 화면을 명세와 나란히 펼쳐 일치 / 부분일치로 분류하고, 어긋난 곳은 원인을 디자인 쪽 / 명세 쪽으로 나눠 분석
Validation
10개 화면 중 8개 일치, 2개 부분 일치. 맞춰야 할 곳 6건 도출(우선순위 높음 2건: 네트워크 실패 안내 문구 분기, 센서 4종 개별 상태 표시). 대조 소요 시간이 2~3일에서 2일로 단축(체감 추정치)
Impact
한 번의 대조로 끝내지 않고, 명세–화면 비교와 문서 간 기준 충돌을 "기계적 수정 / 충돌 / 미정"으로 분류해 보고하는 절차로 반복 가능하게 전환

Case 02 · 복약 설정 — 순서가 꼬일 수 없는 구조

Problem
복약 시간이 섞여 순서가 바뀔 수 있었고, 어르신이 작은 선택지와 복잡한 설정 화면을 다루기 어려웠다
Why
안내 문구를 늘리는 방식으로는 실수를 막을 수 없다. 구조 자체가 실수를 허용하지 않아야 한다
Hypothesis
시간대별 화면을 분리하고 설정 범위를 겹치지 않게 하면, 어떤 값을 선택해도 순서가 유지되고 실수가 구조적으로 불가능해질 것이다
Design
아침(4~10시)·점심(11~15시)·저녁(16~23시) 3개 화면으로 분리, 숫자 직접 입력 대신 선택식 UI, 미래 칸은 입력 자체를 차단, 복용/미복용/95분 무응답 3분류 + 음성 응답, 재알림 2회(+5분, +30분)
Validation
개발팀의 질문에서 예외 케이스(기기 꺼짐 후 재부팅, 네트워크 단절, 알림 시각 겹침) 정리를 시작. "한 화면에 세 시간대를 모두 두는 안"은 글씨가 작아져 어르신이 보기 어려워 폐기
Impact
어떤 값을 선택해도 순서가 꼬이지 않는 설정 구조 확보. 이후 반복 점검을 거치며 "무이용"→"무활동", "시간이예요"→"시간이에요" 등 문구·용어를 통일

Case 03 · 위험관리 알림 — "누가 지금 움직여야 하는가"

Problem
알림이 8종(복약, 화재, 배터리 2단계, 인터넷, 원격지원, 메시지, 응급)이고 종류마다 문구·버튼·재알림·닫히는 조건이 달랐다. 응급 호출은 놓치면 안 되지만 오작동으로 잘못 걸려도 안 된다
Why
알림의 양이 아니라 "누가 지금 움직여야 하는가"가 기준이어야 한다. 놓침과 오작동 사이에서 균형을 잡아야 한다
Hypothesis
우선순위를 나누고 확인 절차를 두면, 중요한 알림은 놓치지 않으면서 오작동 대응도 줄일 수 있을 것이다
Design
알림을 긴급(화재·응급) > 시스템(배터리·인터넷·원격지원) > 일상 요청·응답(복약·메시지) 3등급으로 분류. 여러 알림이 겹치면 발생 시각순으로 쌓고 소리는 최상단 1건만. 응급 알림에는 15초 확인창 + 취소 방법 3가지(화면·물리버튼·음성), 물리 버튼 충돌과 재부팅 중 발생까지 예외 설계
Validation
위험 대응 기준(무엇을 응급으로 볼지) 자체는 팀의 정책 결정이었고, 그 위에 올라가는 상세 규칙(확인 시간, 취소 방법, 충돌 우선순위)은 직접 설계해 알림 명세에 반영. 이후 다른 명세(복약·설정·음악·라디오)가 이 규칙을 기준 문서로 인용
Impact
우선순위·누적·예외(버튼 충돌·오작동 취소·재부팅)까지 정리된 알림 체계 확보
05AI Workflow

AI는 도구가 아니라 작업 체계로 썼다

작업 전에 AI의 역할과 검수 기준을 먼저 정했습니다. 정책 결정과 최종 문구는 직접 확정하고, AI에는 초안 작성·반복 작업·누락 항목 확인을 맡겼습니다.

도구쓴 곳평가
Claude 명세 초안, 문구 검수, 문서 정리 (기능명세 12건) 기준을 정해 두면 여러 문서를 같은 틀로 맞추기 쉽다. 명세 작성은 다른 생성형 AI보다 이 쪽이 더 잘 맞았다
Claude MCP × Figma 기능명세 기반 관리자 웹 화면 초안, 스타일 가이드 정형화된 화면은 초안이 빠르다 / 실시간 싱크가 없어 Figma에서 직접 고쳐야 하고, 큰 파일은 섹션을 골라 쓴다
Claude Skills · Claude Code 디자인 규칙·문서 작성 기준 패키지, 명세→문서 변환·변경 감지 도구, 명세·화면 대조 검증 스킬 같은 기준이 유지되고 수작업이 반복 가능한 절차가 된다 / 스킬이 많아지면 충돌해서 역할을 나누고 중복을 없앤다

다른 생성형 AI는 구성 아이디어나 이미지 생성 보조로만 쓰고, 명세 작성·문서 일관성은 Claude로 역할을 나눴습니다. 업무 효율(체감 기준 추정치): 기능명세 1건 작성 3~4일 → 2일, 시안–명세 대조 2~3일 → 2일. 활용 후기를 문서로 정리해 전사에 공유했고, 이 경험을 바탕으로 사내에 AI 활용 방법을 나누는 세미나도 진행했습니다.

06Collaboration

기준이 다른 두 부서 사이에서

"어긋난 항목을 먼저 눈에 보이게 드러내야 협의가 시작된다."

위험 케이스 분류와 알림 시간 같은 기준을 사업부와 기획팀이 다르게 보고 있었고, 그 영향으로 기기와 관제센터 기능명세서도 서로 어긋나 있었습니다.

내가 한 일두 명세서를 대조해 달랐던 점을 찾아내고, 기기 기능명세서를 수정
팀이 정한 것기준 자체(무엇을 위험으로 볼지)는 사업부와 기획팀이 협의해 정했고, 그 결정을 명세에 반영
결과두 문서의 기준이 맞춰짐
이후 만든 장치정책이 바뀔 때 문서 사이 기준이 어긋나는 일이 반복돼서, 충돌을 "기계적 수정 / 충돌 / 미정"으로 나눠 보고하는 정합 점검 절차를 만듦
07Outcome

그 결과 무엇을 얻었나

문제해결결과
같은 규칙이 여러 명세에 중복되고 알림마다 동작이 달랐다 공통 규칙을 상위 기준 문서에 두고 하위 명세는 참조, 알림을 우선순위 3등급으로 정리 알림 명세 56KB → 37KB(약 34% 감소), 공통 규칙 15개 → 6개
시안과 명세가 일부 맞지 않았다 화면 단위로 대조하고 원인을 디자인·명세 쪽으로 나눔 설치 플로우 10개 화면 중 8개 일치, 동기화 6건 도출
복약 시간이 섞여 순서가 바뀔 수 있었다 아침·점심·저녁 설정 범위를 겹치지 않게 분리 어떤 값을 골라도 순서가 유지되는 설정 구조
응급 알림을 놓치면 안 되고, 오작동으로 잘못 걸려도 안 된다 15초 확인 창과 취소 방법 3가지, 물리 버튼 충돌·재부팅 예외까지 설계 우선순위·누적·예외까지 정리된 알림 체계
08Learnings

배운 것, 그리고 다음에 검증할 것

안 띄우는 것도 설계입니다. 알림의 양보다 "누가 지금 움직여야 하는가"가 기준입니다. 시안만으로는 정해지지 않는 규칙이 남고, 이를 확정 / 미확정 / 개발 확인으로 구분해 보이게 하는 것까지가 설계자의 일이라고 생각했습니다. AI는 초안과 대조에 강하고, 판단과 확정은 사람이 해야 한다는 것도 배웠습니다. 다시 한다면 AI 작업 규칙(역할·검수 기준)을 초반에 정해 두고 시작할 것입니다.

아직 검증하지 못한 것: 이용자를 직접 인터뷰하지는 못했습니다. 현장 운영자·어르신·보호자 페르소나는 운영 조직이 모은 자료를 토대로 구성했습니다.

다음 계획: 자유대화는 사용성·정확도 검증 단계이고, 오탐지나 출동 감소 같은 제품 효과는 그 검증이 끝난 뒤 정리할 계획입니다.

09Closing

화면만 설계하는 디자이너가 아니다

사용자의 문제에서 출발해 가설을 세우고, 기술과 비즈니스를 연결하며, 제품 경험과 팀이 일하는 방식까지 설계합니다. AI는 초안과 반복 작업, 대조를 맡기는 도구로 쓰고, 판단과 책임은 제가 집니다. 그렇게 더 나은 제품을 만들어가는 Product Designer입니다.
